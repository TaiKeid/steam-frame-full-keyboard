# Configuration and VR switching

File-based layouts, language support and editable themes are core requirements. Users must be able to add profiles, then select them inside VR without recompiling or restarting the keyboard.

The app implements runtime profiles, VR selectors, reload and persistent selection. The bundled resources are also embedded for fallback. Bundled XKB profiles cover English, the major European languages, Turkish, Greek, Arabic, Persian, Hebrew, Hindi, Thai, Vietnamese, Indonesian, Malay, Filipino, Georgian, Armenian, Kazakh and Azerbaijani; [languages and system settings](languages.md) lists them. The normal libei/Gamescope path resolves characters locally and sends Unicode, independently of system layouts. Physical uinput and external JIS still require a matching `--target-language` declaration; application coverage varies. Integrated Japanese, Chinese and Korean composition is available; see [languages and system settings](languages.md).

## Independent profiles

| Profile | Owns | Example |
| --- | --- | --- |
| Layout | Key positions, sizes, physical key IDs and shortcut actions | `layouts/en-us.json`, `layouts/international.json` |
| Language | Input keymap, key legends, locale and font preferences | `languages/en-us.json`, `languages/de-de.json` |
| Theme | Colors, gradients, rounding, sides, press movement and animation timing | `themes/graphite.json` |
| Settings | Default profile IDs, favorite layout/language pairs, pin and Focus mode state | `config/default.json` |

Keep these separate. The same geometry can display English or German legends, and a theme can apply to either language. A favorite saves a layout/language pair for cycling from the main keyboard. Cycling preserves the active theme. Favorite records contain `id`, `name`, `layout` and `language`. The legacy `theme` field is optional, retained when saving, and does not affect cycling. Full-size is the default, but the runtime must not assume a fixed key count or hardcode their arrangement.

The current `en-us-full` layout ID identifies the approved ANSI geometry and its fallback legends. Its name does not restrict it to English. Languages declare `required_keys` as physical action names. The German profile requires `IntlBackslash`, provided by `international-full`. Activation rejects a layout missing that key. This international variant retains the rectangular Enter from the approved design.

A layout may name its usual `language`. Settings dims languages the pending layout cannot type, and choosing a layout that cannot type the current language switches the language: first to a favorite pair with that layout, then to another variant of the same language (preferring the layout's own), then to the layout's `language`, then to US English. A layout with `flick` keys serves only a language whose `flick` map has every one of its slots, and a flick language needs every slot of its `flick` map as a key of the layout, except the Japanese `mode`, `undo` and `script` slots: a layout without the mode key shows the toolbar's あ / A button instead, and one without ↶ or the script key simply has none. A Japanese flick layout may name its English page in `latin_layout`; that layout sets `companion` to `true`, which keeps it out of Settings and the Additional languages popup, so it can't be chosen by itself. It should have the same size as the layout it belongs to. Japanese flick therefore pairs only with its own 12-key layout.

## File locations and discovery

Packaged defaults live in the versioned installation's `share/framekeyboard/layouts/`, `share/framekeyboard/languages/`, and `share/framekeyboard/themes/` directories. User files live under `$XDG_CONFIG_HOME/framekeyboard`, defaulting to `~/.config/framekeyboard`:

```text
config.json
layouts/*.json
languages/*.json
themes/*.json
```

The installer must preserve user files during updates and must not rewrite them with bundled defaults. The OS image is not a configuration store. Each profile has a stable `id`, a display `name`, and a `schema_version`. Settings reference IDs, not absolute paths. A user profile with the same ID can override a bundled profile; the VR picker shows its display name. Reject duplicate IDs within a source directory instead of depending on filesystem order.

Keep a compiled safe default available. If a user override is invalid, retain the last validated profile and show its filename and error in settings. On a cold start, fall back to the bundled profile or compiled default. Unknown schema versions must not be guessed or silently rewritten.

## Layouts and styles

Layout JSON defines key rectangles and actions. An action's `kind` is `key` (a physical key name), `shortcut` (`copy`, `cut` or `paste`), `flick` (a slot name of the language's `flick` map; it never sends a physical key), `emoji` (`picker`) or `dictation` (`mic`, which opens dictation mode and is shown only when dictation is usable). An optional `icon` field accepts `copy`, `cut`, `paste`, `steam-frame`, `steam-os`, `backspace`, `delete-left` (Backspace as phones draw it, a tag pointing left with × in it, as on the Japanese flick layout), `emoji`, `mic`, `space` or `enter`; omitting it renders the text label. Icons use the theme legend color and move with the key face. Modifiers latch on tap by default: the next key gets them, then they release. Holding a Shift key for 0.5 s without another key locks it, as on a phone keyboard: it applies to every key, for example to select text with the arrows, until the next Shift press unlocks it. Shift keys show an arrow before their legend, filled while locked. Hiding the keyboard ends the lock. Set a key's `sticky` field to `false` for a native press/release hold; bundled right Super uses this for the desktop menu. The existing validator checks bounds and overlap. The runtime validator limits profile size, key count, label length and action types. Profiles are data and cannot execute commands or scripts.

Theme JSON defines renderer properties directly. Support surface and legend colors, key-face gradients, side colors/depth, corner radii, spacing/padding and font sizing, plus hover, pressed, latched and disabled state styles. The current renderer consumes the graphite fields plus `font_size`, `small_font_size`, `padding`, `hover` and `latched`. It uses immediate hover/latched colors and animated press travel. The `disabled` color blends with the legend color to dim unavailable settings controls, toolbar buttons and keys; a disabled key's cap also sinks flat, as a disabled button does. Optional `warning` and `error` colors set the amber and red notice text; by default they are light on themes with a light legend and deeper on themes with a dark legend. Optional `alert` colors status icons that need attention, such as Focus mode typing into a window out of sight. It defaults to the warning color on themes with a light legend and to a saturated orange on themes with a dark legend, where the deep warning amber would look like the legend on a thin stroke. A theme whose legend is dark is a light theme: its recessed fields (the dictation editor, emoji grid, text fields and switch tracks) turn lighter than the case instead of darker, its idle scrollbars take a shade of the legend instead of the hover color, and a hovered key or button keeps its own shading, tinted evenly by the hover color. The latched color fills latched keys, selected buttons and menu items, the selected emoji tab and switches that are on. Optional `latched_top` and `latched_bottom` turn that fill into a gradient through `latched`, and `latched_legend` sets the text and icons drawn on it (the legend color by default), so a bright latch can carry dark text. `latched_finish` is `flat` (the default) or `neon`. Neon draws a dark face inside a glowing tube colored from `latched_top` through `latched` to `latched_bottom`; a pressed key lights the same tube as it travels down. Optional `edge` draws a line just inside every keycap and button face, including toolbar buttons, dropdowns, candidates and emoji tabs, and rims the recessed fields, switch tracks and Settings cards in a dimmer shade of it; `edge_hover` (the edge color by default) is the wider line under the laser and while a key is pressed. Optional `pressed` fills a key held down with that color, its text in `pressed_legend` (the legend color by default). Themes without them have no edges, and a pressed key keeps its face. Per-key fonts, arbitrary spacing rules and additional state styles remain future work. Native rendering does not require CSS or JavaScript theme execution.

Bundled themes: Graphite (the default) and Midnight; the dark Ember, Plum, Crimson, Navy and Mono, each with its own latched accent; Neon (latched and pressed keys outlined by cyan-to-magenta neon tubes) and Cinematic (dark blue with orange accents); the light Porcelain, Blossom and Lilac; and High Contrast, an accessibility theme with white legends and bright white key edges on black, a yellow edge under the laser, solid yellow while a key is pressed and cyan when latched, all text at 7:1 or more.

Validate dimensions and animation limits. In particular, press travel cannot exceed side depth, and painting must stay aligned with hit regions. A theme may change appearance but cannot change the meaning of a key or the input keymap. Geometry changes belong to layout profiles.

## Languages and actual input

A language profile selects a keymap and derives character legends from it, including Shift and AltGr levels. Optional legend overrides are keyed by physical key ID and never change output by themselves. Keep physical positions such as `KeyY` separate from the symbol that a German keymap produces there. Special actions such as Enter and Copy remain explicit actions.

Language profiles have an English `name`, an optional `native_name` as speakers write it, which the Language dropdown and popup show, and an optional `short_name` for the toolbar's language button, which otherwise shows the locale. Language profiles use XKB identifiers. `input_method` defaults to `xkb`; `japanese-romaji`, `japanese-kana` and `japanese-flick` select local composition. A `japanese-flick` profile supplies a `flick` object keyed by slot name; each slot has a `tap` array (the toggle cycle, first entry typed by a single tap) and optional `left`, `up`, `right` and `down` texts. The texts ゛, ゜ and 小 change the preceding kana, and ゛゜小 cycles its variants. An optional `flick_digits` object, with the same slots, gives the digit mode; its texts are typed as they are, at once. The `mode` slot is the 「あA1」 key: a tap moves to the next mode and a flick left, up or right picks kana, English (the layout's `latin_layout` page) or digits; its texts are only its legends. The `undo` slot is ↶ (see [Japanese input](japanese.md#flick-input)). The optional `script` slot is the **Flick Katakana (JP)** key, shown only with that option; its `left` and `right` texts are its hiragana and katakana legends, and it switches between them on a press, without flicks. `chinese-pinyin-simplified`, `chinese-pinyin-traditional`, `chinese-zhuyin`, `chinese-cangjie`, `chinese-quick` and `korean-2set` select local Chinese/Korean composition. Other input methods and nonempty XKB options are rejected. Korean `composition_keys` and `composition_shift` objects supply configurable jamo legends by physical action name; two-set conversion belongs to libhangul. They do not redefine the engine mapping. An optional `latin_toggle`, two-set Korean only, names the key action that switches between Hangul and the layout's own letters, such as `AltRight` for 한/영; that key then stops being a modifier, and its legend comes from `legends.overrides`. Direct Kana profiles supply `kana` and optional `kana_shift` objects mapping physical action names to UTF-8 text. `legends.overrides` maps a key ID to a display string. In normal Frame mode, XKB resolves characters inside the app. A persistent XKB compose state handles dead-key sequences and never consults legend overrides for output. Native shortcuts use the compositor's advertised keymap and active group where available. Only uinput and external JIS retain the frozen launch declaration check, including rules, model, layout, variant and options. Character input never changes global keyboard settings or falls back silently to raw keys when Unicode delivery fails.

Prove US English and German as the first two profiles. German exercises swapped Y/Z, umlauts and AltGr. Additional languages must be addable through files where the backend already supports their input method. Local dead-key composition and Unicode delivery are tested, along with the bundled CJK engines. Arabic and Hebrew keymaps are bundled; when a keymap's letters are a right-to-left script, its character legends are laid out right to left. Arbitrary Compose-key sequences and other IMEs still need explicit capabilities and tests; do not claim support from locale names alone. If a profile needs an unavailable capability, show the reason and leave the working profile active.

Use font fallback and text shaping for non-Latin legends. Treat interface translation separately from typing language; changing the typing language must not unexpectedly change the settings UI language. Do not use the clipboard as an implicit text-insertion fallback.

## Switching inside VR

The main toolbar has Settings, Recenter, Pin, the experimental Stay open over apps button, Focus mode while Replace native keyboard is on, a swipe button while Swipe typing is on, a haptic sounds button while Haptic sounds is on, a Pull for Shift button while Pull for Shift is on and, last of all when additional languages exist, a short language name. The three feature buttons are switches of their own, described under [Swipe typing](#swipe-typing), with Haptic sounds below and under [Pull for Shift](#pull-for-shift). Size is changed with the laser corner resizers beside the case instead. When the case is narrower than the panel (numpad hidden, or the flick layout), the toolbar takes two rows so swipe suggestions fit beside it: Settings, Recenter, Pin and the language on top, and Stay open over apps, Focus mode and the swipe button under Settings, Recenter and Pin. That row holds three buttons, because a fourth would cover the dictation editor, so a fourth and a fifth join the first row, before the language. Swipe suggestions always start after the first row and end before the close button. On full-size layouts, Japanese, Chinese and Korean candidates show in the same place, with ∨ after them opening the rest, and the reading in a line under the toolbar (see [Japanese input](japanese.md)). The pin changes its icon when enabled without an active background; so do Stay open over apps and Focus mode when on. Pin prevents both movement methods and resizing, and hides the line and corner resizers. Its state is saved immediately in the optional boolean `pinned` field of `config.json`. It does not stop dashboard following or recentering. Missing `pinned` defaults to false. A new install has no favorites.

**Stay open over apps** is an experimental toggle. Its state is saved immediately in the optional boolean `passthrough` field of `config.json`, whether the button or a pinned window's request changed it, and the next launch starts with it; a missing field means off. Under a shell it is ignored. While it is on, closing the dashboard leaves the keyboard open at its current place, and typing goes to the Frame app with compositor keyboard focus. Outside the dashboard the panel takes no SteamVR laser events, so it never claims the scene's controllers. Full Keyboard reads each Frame controller's pose, trigger and bumper itself: point at a key and pull the trigger or press the bumper, as in the dashboard. The app receives that trigger or bumper press too. A dot marks where each controller points, and the keyboard highlights the key under it. Grip and handle movement work as in the dashboard. Pointing at a window floating in the world brings SteamVR's own laser for as long as the ray stays on it or just below it, where SteamVR then shows the window's controls, plus 0.3 s, so a trigger pull clicks that window and gives it focus; Full Keyboard's own ray cannot click another app's window. While SteamVR's laser shows, a running game does not receive the controllers. Opening the dashboard returns to SteamVR's laser; any key held across the change is released. Turning the toggle off while the dashboard is closed hides the keyboard. With Replace native keyboard enabled, a keyboard request from a window pinned in the world while the dashboard is closed turns the toggle on and opens Full Keyboard there, once per request. A request that opened inside the dashboard never turns it on, including when the dashboard closes while that request is still open. Turning it off again while the dashboard is closed hides the keyboard and ends that request as X does, so the next keyboard button press opens Full Keyboard at once. Passthrough turned on by a request stays on after that request ends, as if the toggle had been pressed; this is intended.

**Focus mode** (saved as `keep_open`), a window icon that is slashed while off, is shown only while Replace native keyboard is on in VR. Without replacement no request closes the panel, so the button would do nothing. Its state is saved immediately in the optional boolean `keep_open` field of `config.json`; a missing field means off, and the field is ignored while replacement is off. While it is on, the panel stays where it is when its keyboard request ends: a Steam field losing focus or closing, Esc in a Steam field, or a local app's request closing. With no request open, typing goes to the app with compositor keyboard focus, as it does with replacement off, so a desktop app such as a text editor can be typed into without pressing its keyboard button. This includes dictation's Send while Focus mode holds the panel. Steam's own fields still need a field selected: clicking one makes it the target again. While a new request is being taken over, for example while Steam's keyboard closes, nothing is sent until it is ready. The next request from any Steam field or app takes over the open panel in place, releasing held keys and dropping queued input as on any target change. X hides the panel and ends the request as before; Focus mode stays on but holds nothing until a request or launch shows the panel again. The native keyboard button closes the panel the same way, through X's own path, so it also discards dictation's editor as X does; whether it ends the open request or, with no field open, starts a new one, that new request is ended once the panel has acknowledged it, since the bridge refuses to end an unacknowledged request and would otherwise give it to Steam's keyboard; the next press opens Full Keyboard again. Use Steam keyboard, the stall watchdog and other fallbacks to Steam's keyboard hide it the same way. So does Steam's keyboard opening for a field Full Keyboard cannot type into, such as one in an embedded web page like the Steam Store's search: only one keyboard shows, and typing never goes to the game or app behind that field. Closing the dashboard still hides it unless Stay open over apps is on, and reopening the dashboard brings a held panel back. Turning Focus mode off while no request is open hides the panel. While the held panel types into the focused window and that window is out of sight, the window icon turns the theme's `alert` colour, orange by default. Gamescope names each window's SteamVR overlay after the window's title, so the overlay named like the focused window is its own. A name counts only while no other window the keyboard has seen, and that is still open, has the same title, such as two empty documents of one editor, and, after the focused window's title changes, only once the overlay names were read 0.3 s later or more, as Gamescope renames the overlay just after. Otherwise, and when no single overlay has that name, the keyboard learns the link when focus moves from one window to another: the newly focused window is the one app window in sight then. Focus seen for the first time, or again after the panel was hidden, teaches nothing. The keyboard looks for window overlays only while the panel is shown. With several windows in sight at that moment, such as a pinned window beside the one clicked, the window overlay the dashboard laser points at is taken; if the laser is on none of them the link stays unknown and no warning is shown; with no app window in sight at all, it is shown. A Steam game uses its own overlay's visibility. The cue also covers a local app's open field, so typing into a window that went out of sight, for example with Stay open over apps after the dashboard closed, is flagged too. While it shows, a tooltip above the button names that window by its title (SteamOS's Desktop as KDE Desktop), unless Integration → Hidden window tooltip is off.

**Steam's dashboard has focus:** with no Steam field selected, nothing is typed while the dashboard is the window Gamescope sends keys to, with or without Focus mode. Otherwise keys would reach whichever app Gamescope falls back to, such as a browser behind the dashboard. Only the dashboard's own page window counts: hovering its bottom bar gives the bar and its popups the keys for a moment without any choice made. Gamescope gives that window its keys when it is clicked, and moves them on to the focused app soon after the laser uses the keyboard, so the keyboard treats the dashboard as focused from a click on it until a trigger pull off the keyboard leaves an app window focused, another app takes focus, or the dashboard closes. Clicking a text field, or the window to type into, types again. After waking, click inside the target window to restore lost focus before typing. A key pressed meanwhile moves but sends nothing, and the Focus mode icon shakes inside its button instead of a status message; so does any typing refused because there is no target, such as Focus mode holding the panel without a field. Without Replace native keyboard there is no Focus mode button, so a message says "Click the window you want to type into first." instead, until that window has the keys. App clicks are checked against focus observations begun after the click, so an older dashboard observation cannot erase the selection. The keyboard sees a click as the trigger starts to move, but SteamVR clicks only deep in the pull, so Steam's page can still have the keys just after a click that went elsewhere. What SteamVR's laser was on when the pull began decides. A click inside an app window waits up to a second for that window to get the keys, and chooses the app with them only while that app's window is in sight: a light pull that clicks nothing leaves typing blocked when the keys fall back to an app out of sight. A click on the dashboard's bar, such as an app's icon, waits for the bar to take the keys and chooses the app only if that app's window is then in sight, in the dashboard or floating in the world: Steam's icon, the bar's keyboard button and the other buttons leave typing blocked, as the app stays out of sight behind Steam's page. A click on Steam's page, or anywhere else, ends with Steam's page seen after it. A pull with the hand SteamVR's laser is not on is placed by that hand's own ray, as the laser's target belongs to the other hand. One that can choose no app, such as a twitch of that trigger while its hand points at Steam's page or at nothing, leaves the other hand's click on the bar or in a window waiting. Sleep discards in-flight focus observations and click intent, retaining the dashboard typing protection until fresh focus and a deliberate app choice allow typing. The keyboard reads Gamescope's keyboard focus on `:0` ten times a second while the panel shows in the dashboard, and each Frame controller's trigger twenty times a second while the panel shows in the dashboard and that controller's laser is off the keyboard, so a click just before Steam's page takes the keys still counts.

Settings has Back, Apply and save, and Reload config icons at the top left. Five cards sit in a row that scrolls sideways; three show in full and the start of the fourth is cut off at the right. Every card row puts its label at the left edge and its dropdown, switch or field at the right edge; labels have no trailing colon. The Languages and Layouts card contains Layout and Language dropdowns, the Additional languages button, which shows how many are set, the Swipe typing, Typing suggestions and Pull for Shift switches, the Japanese options described under [Japanese learning](#japanese-learning), and [Clear learned words](#clear-learned-words) last. A theme chosen in Settings shows at once; Back returns to the saved one. The cards scroll with the stick, gliding to each step, or by pressing on them and dragging with the laser; scrollbars light up white under the laser and while dragged. The General card contains Theme and Background dropdowns and Hide numpad, Grab to move and Auto leveling switches. The Typing card contains the Haptic sounds dropdown, with its effect and volume while sounds are on, the Close emoji picker after choosing switch, the KDE Desktop Unicode dropdown with a description of its choice below it, and the Extended key collision switch. The Dictation card contains the Dictation mode; with dictation on it also shows Send and Type as I speak, the Model row on device, and the Server address, a Connection Test and the fallback when self-hosted. The Integration card contains Replace native keyboard, Start with SteamOS and Hidden window tooltip switches. Start with SteamOS and Hidden window tooltip are disabled while replacement is off. Dropdowns have no search and show up to five choices. A choice whose name is too long for the list scrolls while the laser is on it: it waits 0.8 s, scrolls to its end, rests, then starts over. Scroll with the stick, or by pressing on the list and dragging, to reach the rest; click a choice to select it, or click outside the list to dismiss it. Dismissal consumes that click. Escape in the desktop preview dismisses a list first, then leaves Settings.

The card row scrolls horizontally when more cards are added. Each card has its own vertical scroll offset when its contents overflow. Cards and fields outside their viewports are hidden from painting and hit testing. Dropdowns are drawn and hit-tested above those clips and can extend beyond the keyboard case. Use scroll input or drag a scrollbar with the trigger. In the desktop preview, Shift plus the mouse wheel scrolls horizontally. A vertical wheel over a card with no vertical overflow scrolls the card row. The production UI has five cards, Languages and Layouts, General, Typing, Dictation and Integration; builds other than releases add a Debug card last ([debug mode](building.md#debug-mode)). Automated tests supply extra cards and fields to exercise both axes.

Num Lock is saved immediately as the optional global boolean `num_lock`, defaulting to false. It survives closing, reopening, layout changes and favorite cycling. Restoring it sets local legends and Unicode mapping without sending startup input. In physical uinput and external JIS modes, keypad input first reconciles the target lock through reported LED or XKB modifier state. If synchronization is needed, the panel asks you to press the keypad key again after feedback arrives. Targets without lock feedback cannot receive lock-dependent keypad input safely; ordinary keys remain available.

The General card's Background dropdown sets the case behind the keys: **Visible** (the default) fills it; **Semi-transparent** draws it at 50% opacity (15% in light themes, whose pale case reads far brighter), so the dashboard or app shows through it dimmed; **Invisible** leaves it transparent, so the dashboard or app shows through. Either way the whole case still takes the laser. With any choice but Visible, keycaps, legends, toolbar buttons, the emoji picker, the dictation editor and popups keep their theme, and Settings keeps its opaque case so its cards stay legible. Text drawn on the case itself (dictation mode's status line, the reading line and its hint, the dictation counter) sits on a small plate of the case colour fitted to it, so it reads over a bright or a dark background; the flick preview keeps the case-coloured gutters around its caps. It is saved as the optional global string `background_surface`, `visible`, `semi-transparent` or `invisible`, defaulting to `visible`. A saved `disabled`, a choice that let the laser through the case's gaps and was removed, loads as `invisible`; another value is reported and treated as `visible`. It applies to every layout and favorite. Apply and save activates it; Back discards the pending change.

The Typing card's **Haptic sounds** dropdown adds a pop to keyboard keys: **Off** (the default), **Press**, **Release** or **Press & release**, saved as the optional global string `haptic_sounds`. Release pops a little higher than press. Sounds fall where haptics do: a swipe pops when it starts and ends, not for each key crossed, and a held key pops once. They are silent while the microphone is listening. With sounds on, two more rows appear: **Haptic effect** picks one of six pops, three pitches each plain and then with a click (`haptic_effect`, `a` to `f`, `e` by default). Each icon is a note on three lines: higher for a higher pitch, with a ring around it for the click, and **Haptic volume** picks 25, 50, 75 or 100% loudness (`haptic_volume`, 75 by default). The steps follow hearing rather than signal level, so 50% sounds about half as loud as 100%, and all of them scale with the system volume. Clicking either one previews the sound, even on the current choice: press, release or both, as chosen above. The pops are synthesized when first needed and kept in memory, with no sound files. A pointer entering any keyboard surface starts the output stream, which stays warm while any pointer remains there. It closes two seconds after the last pointer leaves, and immediately on hide, headset removal, mute or listening. Showing the keyboard alone does not start audio. Without PipeWire the keyboard stays silent.

With Haptic sounds on, the toolbar shows a haptic sounds button, saved as the optional global boolean `haptic_sounds_switch`, true by default. It is a switch of its own: it mutes and unmutes keys, survives restarts, and leaves the dropdown as it is, and Settings previews respect its mute state. With Haptic sounds at Off the button is hidden. While the microphone is listening or recognition is still working, it is disabled like the language button, and crossed while keys are silent.

The Typing card's **Key vibration** checkbox turns the keyboard's own vibration pulses on or off: the hover tick, the press and release clicks and the flick tick of Pull for Shift. The controller's own click on trigger press is not the keyboard's and stays. It is saved as the optional global boolean `vibration`, true by default, and applies with **Apply and save** like the other Typing card choices. It leaves **Haptic sounds** and dictation's listening cues alone: those are switches of their own. A shell that plays haptics itself receives no `haptic` events while it is off.

The General card's Hide numpad checkbox removes Num Lock and all Numpad keys, narrows the case, and keeps the remaining keys at the same size. It is saved as the optional global boolean `hide_numpad`, defaulting to false, and applies to every layout and favorite. Showing the numpad again restores its remembered Num Lock state. The transparent space beside the narrower case is excluded from VR interaction. Settings retains its full card area.

Checkbox edits stay pending across dropdown selections. Apply and save activates the chosen profiles and saves all pending additional languages, numpad visibility and movement behavior; Back discards pending edits. At most 32 favorite records can be saved.

The main language button cycles through the default saved by Apply and save, then unique valid favorites in saved order. A default that is already a favorite appears once. If the only favorite matches the default, the button has no other state to cycle to. Invalid or unavailable favorites are skipped. Cycling changes the current keyboard without replacing the saved default. Saving pin state while on a favorite also preserves that default. Reload rereads profiles, favorites, pin state, Num Lock and numpad visibility, closes dropdowns, cancels UI captures, and resets pending edits while retaining the current active keyboard. A config edit that cannot be read reports an error and retains the last loaded global settings and favorites; an invalid optional value is reported and falls back on its own, while the values beside it load. Newly added profile files appear after reload; an automatic file watcher is optional.

Japanese Romaji, Kana and external JIS modes are choices in the Language dropdown. They use the same compatibility validation and Apply path as other languages.

Validate and prepare a candidate configuration off to the side. On Apply, cancel active pointer presses, stop repeat and release held keys through the old backend before changing mappings. Clear latched modifiers, replace geometry and hit regions together, and redraw. Preserve the target application's focus. A failed apply keeps the previous working configuration and reports the error in VR.

Persist successful selection to `config.json` using an atomic write. If saving fails, keep the usable runtime configuration and report that it will not survive restart. Reloading files must not overwrite unrelated favorites or silently activate an edited profile while a key is held. The active selection survives app restart; the installer preserves user files across application updates. Reload releases held keys and reloads favorites. After Apply or Reload, typing requires `--start-enabled`, a live backend, and an available Unicode connection. Only physical uinput/external JIS require the selected language to match the declared target keymap. In those physical modes, a saved mismatch also permits startup with Settings accessible. A mismatch leaves the panel visible but input-disabled until a matching profile is selected or the app is reopened with matching target options. It keeps the active selection rather than activating a config.json edit behind the user's back.

## Swipe typing

The Languages and Layouts card has a **Swipe typing** checkbox, saved as the optional global boolean `swipe_typing` and defaulting to false. Apply and save activates it; Back discards it. A smaller second line under its label reads "Powered by FUTO Swipe" whether or not swipe is available, as the model license requires; it dims together with the checkbox.

With Swipe typing on, the toolbar shows a swipe button, saved as the optional global boolean `swipe_switch`, true by default. It is a switch of its own: it turns swiping on and off, survives restarts, and leaves the checkbox as it is, which still decides the marks in Additional languages. With the checkbox off the button is hidden. If neither the main language nor an additional one can swipe, the button is greyed out and crossed, and a press only shakes its icon, fading from the alert colour. On a flick layout it is greyed out, crossed and ignores presses. On any other language that can't swipe, while another of the user's languages can, its icon is greyed out but it still toggles. In a field a shell marks as a password or PIN field, which takes no swipes and no typing suggestions, it shows a lock instead, and a press only shakes it. Japanese, Chinese and Korean still compose there and offer their candidates, but learn nothing, and Japanese offers nothing it learned ([Japanese learning](japanese.md#learning)). In the dictation editor it is greyed out and crossed whenever the editor can't be typed in: while the microphone is listening, recognition is working or text is sending.

The checkbox is disabled unless the language chosen in the dropdown or an additional one has `"swipe": {"lexicon": "<id>"}`, uses the `xkb` input method or Pinyin, the swipe engine module and model are installed, and a word list `swipe/lexicons/<id>.tsv` exists. An optional `"replace"` object in `swipe` respells the word list for a language, such as `{"ß": "ss"}` for Swiss German. A user file in `$XDG_CONFIG_HOME/framekeyboard/swipe/lexicons/` overrides the bundled one; Reload rereads it. The saved choice is kept while disabled. Swipe is active only when it is saved on and the active language supports it, so cycling to a favorite without swipe support switches it off for that language. Bundled support: English (US, UK), German, French (not Canadian), Spanish, Italian, Portuguese, Polish, Dutch, Swedish, Ukrainian, Russian, Czech, Slovak, Danish, Norwegian, Finnish, Estonian, Latvian, Lithuanian, Hungarian, Romanian, Croatian, Serbian (Cyrillic and Latin), Slovenian, Bulgarian, Macedonian, Greek, Turkish, Catalan, Icelandic, Indonesian, Filipino, Vietnamese, Azerbaijani, Arabic, Hebrew and both Chinese Pinyin profiles. Bulgarian's two phonetic layouts type ю or ч on the number row, so words with them can't be swiped there, only typed. Japanese, Korean and external JIS have no swipe yet.

Swiping works on the normal keyboard and in the dictation editor, except while it is listening or sending. In the editor a word joins the text at the cursor, with a space when it follows a character, and its alternatives show along the toolbar until another key or a tap in the editor ends them.

While swipe is active, letter keys type on release instead of press, so a press can start a swipe. A press becomes a swipe once the laser is more than a third of a key width outside the start key and half a key width from where it pressed, so a trembling tap near a key's edge still types; a trail follows it. Other keys, modifier chords, a pending dead key and settings controls keep their behavior. Letter keys do not repeat while swipe is active. The best word is typed on release, preceded by a space when the previous output was also a swiped word. A latched Shift capitalizes it, and Caps Lock or a locked Shift uppercases it; otherwise the word list's own case is used. Accented letters without their own key are swiped on the plain letter (é on e, ã on a), and a letter with its own key keeps it under an accent: Vietnamese ừ is swiped on ư. The number row never swipes, as a phone keyboard has none: its keys type on press, and their letters, such as AZERTY é, è, ç and à, Italian ì, German ß, Russian ё, Vietnamese đ and Arabic ذ, are swiped on the plain letter (ß on s, đ on d, ذ on د). Turkish and Azerbaijani I is swiped on ı, İ on i. Up to five alternatives appear in the toolbar. Choosing one deletes the swiped word and types the alternative. Local apps receive both as one ordered Gamescope text request (`delete_left` actions, then the text), because separate libei Backspace keys could interleave with Gamescope's temporary text keymap and type wrong characters. Steam fields use Backspace keys, which the bridge acknowledges one by one before the text. Any other key, hiding, a profile change, or a failed or timed-out delivery discards the alternatives, because the target's cursor or text may have changed. Pointing away from the keyboard keeps them and the next word's space, as long as the trigger stays at rest: pulling it off the keys, the other hand pointing, or a laser whose trigger cannot be read (controllers other than the Steam Frame's) discards them, because that click may have moved the cursor. A word still being decoded is discarded then too, with a notice. In the Chinese Pinyin profiles a swipe types toneless Pinyin into the composer instead (a tap types one letter there on release), and the composer's own row offers characters; there are no swipe alternatives and no automatic space. Nothing is learned or logged.

A swipe can also start between keys. With [Extended key collision](#extended-key-collision) on, a press there is a press on the nearer letter. With it off, each letter still reaches half the gap to every key beside it for swipes alone, so the letter block has no dead space between letters, while other keys keep their size. A press there that moves becomes a swipe from the nearest letter. One that doesn't types nothing, gives no key feedback, and leaves the last swiped word's alternatives and a latched Shift as they were. Only while a press on a letter would start a swipe; otherwise a gap takes no press.

## Typing suggestions

Under **Swipe typing**, the Languages and Layouts card has **Typing suggestions**, saved as the optional global boolean `typing_suggestions` and on by default. Its second line reads "Completes the word you're typing". Apply and save turns it on or off; Back discards it. It works in the languages swipe typing has a word list for, Chinese Pinyin aside, and is disabled unless the language chosen in the dropdown or an additional one is among them; Japanese, Chinese and Korean keep their own candidates. It does not need Swipe typing on or the swipe engine installed.

While you type a word with the keys, up to five completions of it show in the toolbar, as many as swipe alternatives, where swipe alternatives go, from its first letter. They come from the language's swipe word list (`swipe/lexicons/<id>.tsv`, respelled and overridden from the config folder as for swipe), commonest first. The list is read on a thread of its own at the first letter typed, and let go after five minutes without typing, as while the keyboard is hidden: it takes 3–4 MB. A completion keeps what you typed and adds the rest, in capitals after two or more capitals: Hel offers Hello, HEL offers HELLO. Choosing one types only the missing letters and a space, without the space where a shell asks for none; nothing you typed is deleted, and nothing is corrected. Right after a swipe, the swipe's own alternatives take the toolbar.

The keyboard follows the word from the text its keys type, never by reading the field: letters, combining marks and an apostrophe inside a word add to it, and a space, punctuation, a digit or a symbol ends it. A swiped word counts as typed, so letters tapped after it lengthen it. Backspace takes back what the keys typed a character at a time, also into the words before: deleting the space after a word offers its completions again. Enter, an arrow or any other key that may move the cursor, such as Home, Tab, Delete, a shortcut, Cut or Paste, forgets the word, as do an emoji, another window taking the keys, a trigger pulled off the keyboard, hiding, a phrase that dictation types into the app, and a change of language; typing then starts a new word. Pointing away with the trigger at rest keeps a word being typed, as for swipe alternatives, and so does the other hand taking the laser to type on: only the hand that typed last leaving the keys forgets it, or either hand's trigger pulled off the keys. Backspace past what the keys typed, into the field's own text, or any key held until it repeats, also starts a new word, as the text before the cursor is then unknown. Nothing is suggested or learned in fields a shell marks as password, PIN or terminal fields or as wanting no suggestions, in [terminals](runtime.md), or in the dictation editor, Settings and the emoji picker. In SteamOS's Desktop, suggestions wait until its KWin says which app is active, so a terminal's commands typed meanwhile aren't learned: at most three seconds after the Desktop takes the focus.

Words you use rank higher, each further use by less. A word counts as used when you finish it, typed or swiped, with a space, including the space before the next swiped word, or choose it from the toolbar, and each word typed counts once, also when Backspace steps back into it and it ends there again. One of `. , ! ? ; :` ends a word too, but it counts only once a space follows, as a password can end in one and Enter then send it. A word ended by Enter, Tab, a digit, a symbol, or punctuation without a space doesn't count. Fields marked as password, PIN or terminal learn nothing; elsewhere the keyboard can't tell a password from a word, so a plain word followed by a space counts wherever it is typed. A word the list lacks is offered once you have used it three times. Swear words, slurs and sexual words, listed for each word list in `swipe/lexicons/<id>-offensive.tsv` (overridable in the config folder as the list is), come after every other completion until you have used them once, typed or swiped, then rank like any word, so whoever swears teaches them back; typing more of such a word still completes it. Swipe typing doesn't read that list: a swipe spells the whole word. The counts are kept for each word list in `words/<id>.tsv` in the config folder (`~/.config/framekeyboard/words/`), as word, uses and order of last use, readable by you alone. Each list keeps at most 5,000 words, the one used longest ago going first. They are written two seconds after the last change and as the keyboard exits, and a write that fails is tried again two seconds later. Swiss German shares German's words, as its list writes them: Straße learned in German is offered as Strasse. With Typing suggestions off nothing is learned. [Clear learned words](#clear-learned-words) forgets them by language.

## Clear learned words

**Clear learned words**, the last row of the Languages and Layouts card, is always there, and can't be pressed while nothing is learned or while Japanese learning is being cleared. It opens a list of the languages with something learned, each with a switch, all off: a word list's language by name, such as English (US) or German, with how many words you typed, and Japanese, with "Conversions you chose". **Clear** is enabled once a switch is on and forgets those languages' records; Cancel keeps them. Up to four languages show in one column, more in two or three. It clears Full Keyboard's own records only: the words you typed, and for Japanese its own Anthy record, Mozc profile, phrase choices, completions and next phrases ([Japanese learning](japanese.md#learning)). Steam's keyboard keeps its own. It can't be undone.

## Pull for Shift

Under **Typing suggestions**, the Languages and Layouts card has **Pull for Shift**, saved as the optional global boolean `key_flicks` and defaulting to false. Its second line reads "Pull a key down to type its Shift character". Apply and save turns it on or off; Back discards it. Shells don't see it in the settings they can read and change.

With it on, the toolbar shows a Pull for Shift button, a key with a downward chevron under it, saved as the optional global boolean `key_flicks_switch`, true by default. It is a switch of its own, as the swipe button is: it pauses and resumes Pull for Shift, survives restarts, and leaves the option as it is. Paused, the icon is crossed, keys no longer show the Shift characters they pull to, and they act on press and repeat as they do with the option off. With the option off the button is hidden.

With Pull for Shift on and not paused, a key that types a character types it on release instead of press, and a key pulled down by about 40 % of its height before release types its Shift character instead: 6 then ^, ; then :. While it is pulled, the Shift character slides from the key's corner into its middle and grows as the key's own shrinks away; pulled far enough, the key fills, and VR ticks once. Pulled back up, it types the key itself. The character is the one the key shows, whatever Shift or Caps Lock do; a latched Shift goes with the press, as for any key. Character keys don't repeat while held, whether they are pulled or not. Space, the numpad and keys that edit or move, such as Backspace, Enter, Tab and the arrows, act on press and repeat as before.

Which keys pull to a Shift character:

- Keys whose Shift character differs from their own: the number row, punctuation, and national layouts' own keys. A Shift character that is a dead key composes with the next key, as with Shift.
- Letters pull to their capitals while swipe typing doesn't take them: with Swipe typing off, its toolbar switch off, a language without swipe, or a password field. While swipe is active, a letter starts a swipe instead.
- Japanese kana keys pull to their Shift kana. Korean two-set keys pull to their Shift jamo, ㅃ ㅉ ㄸ ㄲ ㅆ ㅒ ㅖ, which they then show over their own. Romaji and Pinyin letters, which compose lowercase, don't pull; their digits and punctuation do.

Pulled keys also type into the dictation editor.

## Extended key collision

The Typing card's **Extended key collision**, saved as the optional global boolean `extended_key_collision` and on by default, lets a press between two keys of a block reach the nearer one: each key takes the laser up to the middle of gaps no wider than half again the layout's usual gap, so wider gaps between blocks stay empty. The Japanese flick layout's kana and digit pages keep their gaps.

## Japanese learning

Japanese input always learns, as Steam's keyboard does, into a record of its own beside Steam's keyboard's, which it starts from a copy of once, at the first start; there is no setting for it, and an older `japanese_learning` key is dropped on the next save. [Clear learned words](#clear-learned-words), with Japanese switched on in its list, deletes what Full Keyboard learned for Japanese and leaves Steam's keyboard's record as it is. See [Japanese learning](japanese.md#learning).

With Japanese flick as the main language or an additional one, the card also has **Flick Only (JP)**, saved as the optional global boolean `flick_only` and defaulting to false, as on phones. Its second line reads "A quick second tap types the same kana again". With it on, flick taps never cycle (see [Japanese input](japanese.md#flick-input)). Apply and save turns it on or off; Back discards it.

After it comes **Flick Katakana (JP)**, saved as the optional global boolean `flick_katakana` and defaulting to false: most Japanese users never need it, so the key it adds stays out of the way. Its second line reads "Adds a key that switches the kana to katakana". With it on, the flick layout's side column has an あ ア key above Cut, which switches the kana keys between hiragana and katakana (see [Japanese input](japanese.md#flick-input)). Apply and save turns it on or off; Back discards it.

## Emoji picker

The small emoji key at the top of the left column (😊 beside the kana on the Japanese flick layout) opens the emoji picker in place of the keys; its Back key returns. Every bundled layout has the key, as action `{"kind": "emoji", "value": "picker"}` with icon `emoji`; a custom layout without one has no picker. The picker's own keys (space bar, Backspace, Enter and the arrows) are generated from the layout, at its scale and within its visible width, so a hidden numpad keeps the keyboard narrow.

- **Typing:** an emoji types when the trigger is released over the cell it was pressed on, as one Unicode text commit. Dragging more than a few millimeters scrolls instead, and a quick drag keeps gliding after release until it slows to a stop or a press catches it; a glide past either end bounces back to it. The grid, tabs and tone popup give no haptics; the picker's keys do. SteamVR ticks the controller for each discrete scroll step; the keyboard asks for discrete steps only while a laser is over something that scrolls and its stick does not lean toward an end already reached, and for smooth scrolling, which it ignores, otherwise. The thumbstick scrolls too, without gliding: through SteamVR's scroll events in the dashboard, and by reading the stick of the hand pointing at the grid in Stay open over apps, continuously and at the dashboard's speed as measured from its steps. Holding an emoji never repeats it.
- **Skin tones:** holding a toned emoji for half a second opens its six variants, which stay open after the release. Clicking one types it and makes that tone the default for every toned emoji; clicking anywhere else in the picker only closes them.
- **Recent:** the first category, six columns wide whether full or empty, filled down each column, with a Clear button in its bottom-right cell. An emoji chosen from another category moves to the front at once; one chosen from Recent keeps its place.
- **Favorites:** the second category, with a star tab, always shown and at least three columns wide with room for one more. Soft lines in the gaps set Recent and Favorites apart from each other and from the categories. Hold an emoji in Recent for half a second to lift it, then drop it into Favorites; an empty slot shows where it lands. Hold a favorite to lift it, then drop it elsewhere in Favorites to move it, or anywhere outside Favorites to remove it; the lifted emoji fades while a drop would remove it. A toned emoji's hold opens its skin tones first: still holding, moving the laser closes them and lifts the emoji; releasing leaves them open for a click. A lifted emoji near the grid's left or right edge scrolls the grid, and the stick still scrolls it. Favorites keep no tone, so the chosen tone applies, and hold at most 40 emoji. Hiding the keyboard or losing the laser mid-drag changes nothing.
- **Availability:** the key is dimmed and ignores the laser with the uinput backend, with external JIS, while Unicode text delivery is unavailable, or without a color emoji font. The picker closes if delivery is lost while it is open. The language button is dimmed while the picker is open.
- **Closing:** the picker closes on Back, when the keyboard hides, and when Settings opens; the keyboard always reopens on its keys. Typing → **Close emoji picker after choosing**, saved as the optional boolean `emoji_close_on_select` and defaulting to false, also closes it after each emoji.
- **Storage:** `emoji.json` beside `placement.json` (schema 1: `tone` 0–5, up to 64 `recent` emoji and up to 40 `favorites`, the last optional) honors `--config-dir`. It is written when the picker closes, Recent is cleared or Favorites change, and a missing or invalid file starts empty. It records typed emoji, so the app never logs it.

## Dictation

Dictation was released in 0.11.0; the design is in [dictation](dictation.md). The Settings → Dictation card covers the common choices; all of it is stored in `config.json`:

- `dictation`: `"device"` (the default), recognition on the Frame once its model is downloaded; `"server"`; or `"off"`.
- `dictation_device_model`: the on-device model, `"small-q8_0"` (the default); `"small-q5_1"` and `"small-q4_0"` exist for comparison.
- `dictation_fallback`: `true` lets Server mode recognize a phrase on the Frame when the server cannot, once the model is downloaded.
- `developer_options`: `true` shows development-only rows in Settings, such as the on-device model's format.
- `dictation_server`: the user's own speech server as `host` or `host:port`; port 8031 is assumed.
- `dictation_server_source`: `"shell"` when a shell set the server over the [integration protocol](integration.md#dictation), which keeps the editor's text out of its prompts; absent when the user chose it. Choosing or testing a server in the Dictation card removes it.
- `dictation_url`: instead of a server, a full base URL of a hosted OpenAI-compatible provider, such as `https://api.groq.com/openai/v1`.
- `dictation_model`: the model name, for servers and providers that need one.
- `dictation_send_gap_ms`: how many milliseconds Send waits between characters, `10`, `20` (the default), `30` or `40`. Slower keeps characters in order when the Frame is busy.
- `dictation_send_paste`: `true` makes Send, and Type as I speak for each phrase, paste through the clipboard instead of typing; the keyboard writes the clipboard but never reads it.
- `dictation_direct`: `true` turns on Type as I speak: the mic key listens on the normal keyboard, and each phrase is typed into the focused application as soon as it is recognized, without the editor.
- `dictation_recent_servers`: up to five server addresses that passed the Dictation card's Test, newest first, offered when entering the address. Unusable entries are skipped.

Both are the **Send** row of the Dictation card in Settings, which also sets `dictation` (Off, On device or Self-hosted) and shows `dictation_server`, with a **Test** of the connection, and its **Type as I speak** switch sets `dictation_direct`. Each invalid field falls back independently, with a message naming the field. A bad send gap uses 20 ms; a bad Paste or Type as I speak value disables only that option.

The API key for a provider is not stored here, but in `dictation-key` beside `config.json`, readable only by the user (see [speech server setup](speech-server.md#hosted-providers)). A bad mode turns dictation off. A bad server or URL is unset in memory and disables Server mode only when no valid endpoint remains; On device mode is unaffected. Other bad dictation fields use their defaults without changing valid neighboring fields. Saving from Settings preserves the hand-edited URL and model in the file, including invalid values, so their warnings remain until corrected.

A language profile offers dictation with a `dictation` object holding its Whisper language code, for example `"dictation": {"language": "en"}`, and optionally a `prompt` of at most 60 characters that goes before the editor's text in Whisper's prompt, to fix the script or punctuation, for example `"dictation": {"language": "zh", "prompt": "好的，没问题。"}`. Every bundled profile has one except external Japanese JIS, which types through the system's input method. The mic key shows when dictation is configured and the active language has a `dictation` object. With a composer, readings commit into the editor.

In dictation mode the keyboard edits a local editor and sends nothing to the target. The function keys, Tab, Insert, Ctrl, Super, Alt, Steam, Menu, the side column's Cut, Copy and Paste and the emoji key give way to the editor, a Send key, an Undo key, and Cut, Copy and Paste keys that act on the editor alone. A layout without function keys, such as flick, gives the editor the reading line's room, so its keys keep their size. Send takes the right-hand modifiers' place, Tab's without them, or the emoji key's without either; without Esc, the mode adds one in the side column's top slot when that is free. Esc stops listening, leaves an empty editor, or asks before discarding text. Swipe typing works in it whenever it can be typed in, so not while listening, recognizing a phrase or sending.

## Moving the keyboard

The General card has **Grab to move**, saved as the optional boolean `use_drag_to_move`. A smaller second line under its label reads "Hold grip on the keyboard instead of the line". It defaults to false, including for older configurations. When off, hold the trigger on the white line below the keyboard to move it. When on, point at the keyboard and hold grab/grip to move it. The line is hidden in grab mode. Pinning disables both movement methods and hides the line. Apply and save activates this preference; Back discards pending changes.

## Saved VR placement

`placement.json` is separate from profile selection and honors `--config-dir`. Schema 1 stores `space: "standing"`, a decimal-string `universe` ID, a three-by-four rigid `transform`, and `width_m` between 0.45 and 2.0. An optional `dashboard_anchor` stores the last rigid bottom-center dashboard pose. On reopen the saved relative offset is applied to the current dashboard. The `dashboard_full_rotation` flag distinguishes full-orientation bar poses from older yaw-only saves, which migrate without an initial tilt jump. An optional `dashboard_bar` stores the matching bar pose so the bottom-center anchor can follow app tabs while the main tab is hidden. Legacy files without this field remain valid and use their world-space pose until reset. The app writes it atomically on orderly close, including SIGTERM. It stores position, orientation and size, with no key input data. A missing or invalid file recenters on first launch. A relaunch of an already running instance always requests recentering, without reloading this file. The next close saves the new position. Forced termination cannot save the latest movement. A keyboard hosted by a shell keeps its own `placement-hosted.json` in the same format, so neither mode moves the other's keyboard (see [shell integration](integration.md#placement-and-geometry)).

The Typing card also has **KDE Desktop Unicode**, saved as the optional boolean `desktop_unicode_paste` and defaulting to false (Type). It applies only while SteamOS's Desktop has focus, to text with a character beyond printable ASCII, such as emoji, kana or accented letters (see [nested desktops](architecture.md#nested-desktops)):
- **Type** enters each character through the Desktop's IBus as Ctrl+Shift+U, its hex code and Space. The codes are visible at the cursor until each character is complete; slow.
- **Paste** writes the text to the Desktop's clipboard and presses Ctrl+V. Fast, but it replaces what is in the clipboard. The keyboard never reads the clipboard. It sets the Desktop's clipboard through data-control, the standard ext protocol (KWin 6.6 offers only that) or wlroots' older one; where the Desktop's own clipboard can't be set, no Ctrl+V is sent, so nothing the clipboard held before is pasted, and the text is not sent.

The General card also has **Auto leveling**, saved as the optional boolean `auto_leveling`. It defaults to true, including for older configurations. When enabled, the keyboard's long edge is lined up over 500 ms after releasing movement: one end higher than the other (pitch) and a slight turn away (yaw), each within 5° in total, are removed, while the desk tilt around the long edge (roll) is kept. Near the visible dashboard, within 0.6 m of its bottom center, the long edge lines up with the dashboard's, so the keyboard matches a dashboard that is itself slightly rolled. Elsewhere, and with the dashboard closed, it lines up level and square to where you were when you released, recentered or restored it; it does not turn to follow you afterwards. Once the keyboard has been shown with the dashboard closed (Stay open over apps), it keeps that room leveling, even when the dashboard opens again, until you move or recenter it. When the dashboard carries the keyboard to a new heading, the room leveling turns by the same amount. A larger deliberate turn is kept. Switching between the two eases the same way. When disabled, the chosen roll remains unchanged. Applying or reloading a change preserves the displayed pose; enabling starts a fresh easing interval. Back discards pending changes.

## Optional native keyboard replacement

Integration → Replace native keyboard is saved as the optional boolean `replace_native_keyboard`, defaulting to false. Apply and save activates the preference; Back discards pending edits. The installed VR launch must have typing enabled, a working libei/Unicode backend and access to Steam's existing local debugger at `127.0.0.1:8080`. This dependency applies only to replacement. Enabling the option leaves Developer Mode, ports, system services and autostart unchanged. Missing requirements leave replacement inactive and Steam's keyboard usable. Settings exposes **Use Steam keyboard** during an active native request while this option is on. That action restores native for the current request; future requests may use Full Keyboard again. See [connection requirements, coverage and failure behavior](native-replacement.md).

With replacement enabled in VR, the main × dismisses the typing session and hides the panel while the app stays resident. Native summon requests can then reopen Full Keyboard without another manual launch. **Quit Full Keyboard** is shown only in Settings while replacement is enabled; that action exits the app and restores native fallback. With replacement disabled, × retains its normal quit behavior.

## Additional languages

The Additional languages button opens a popup over Settings: one well with three columns.

- **Layout** lists the layouts as tabs. The tab only chooses which layout the Languages column adds to; it doesn't change the main language.
- **Languages** lists every language in two columns, those the tab's layout can type first. The rest stay listed, dimmed, and can't be added. A check marks a pair already in use. While Swipe typing is on, a trail icon marks languages that can swipe, and a slashed one those that can't; with it off, or without the swipe engine, neither shows. Dragging up or down scrolls the list.
- **Main language** always holds a pair, English (US) on US QWERTY by default. It's the same pair as the Layout and Language dropdowns, and it stays the same while the toolbar button cycles languages. Apply keeps the language being typed in unless the main language changed or that language was removed. Its reset button returns to that default, removing it from the additional list if it was there, and is off while it's already the main language.
- **Additional** holds the pairs the toolbar's language button cycles through after the main language, in order, up to 32. The eraser clears them after asking, and leaves the main language.

Tapping a language adds it to the end of Additional. Dragging one sideways lifts it, so it can be dropped where it should go. Dropping it on the main slot replaces the main language, which becomes the first additional one, so making Korean main keeps English a tap away. Rows in Additional drag to reorder. Dropped on the main slot, a row trades places with the main language; dropped anywhere else, it's removed. A pair whose layout or language file is gone stays listed, marked missing, so it can be removed. The lists scroll with the stick.

The pairs are saved as the optional `favorites` array in `config.json`. Legacy repeats and entries matching the main language show once or not at all, and are dropped by the next Apply.

Like every Settings change, these edits are saved by Apply and discarded by Back. The back arrow only returns to Settings. If the popup changed anything, leaving Settings asks whether to save or discard; Save does what Apply does. Dropdown changes alone don't ask.

## Updates

The Settings header has a centered Check for updates button, with the running version in faint text beside it. Its latest-version message resets after five seconds; an available update remains offered until the process exits. The keyboard also checks silently every few hours, and a dot on the main toolbar's Settings button marks an offer. This state is not a saved preference. Download and install update verifies, stages and restarts into the newest stable GitHub release. It preserves configuration and placement. See [updates](updates.md).

Integration → Hidden window tooltip is saved as the optional boolean `focus_tooltip`, defaulting to true; it applies only with Focus mode, so only while replacement is on.

Integration → Start with SteamOS is saved as the optional boolean `start_with_steamos`, defaulting to false. Its choice is remembered while replacement is off, but startup is active only when both saved booleans are true. Applying either option updates the user-local startup unit on the preference worker; the VR loop keeps running. See [background startup](native-replacement.md#start-with-steamos).

Saving VR preferences couples the replacement and startup booleans to the startup-unit transaction. If unit configuration fails, other preferences still save, those two saved booleans keep their prior values, and a separate startup warning explains which changes were not saved. If the JSON write itself fails, the previous unit and enablement link are restored and the user manager is refreshed. A later successful save clears the warning or error.

Reload also reconciles the startup unit with valid saved settings on the same worker. It does not rewrite JSON or activate an edited profile. A failed reconciliation reports a startup configuration error; Reload retries it. Preview and render modes do not configure startup.
