# Build from source

Most users should install the ARM64 archive described in the [README](../README.md). These instructions are for development and release packaging. Build on a Linux development machine; a host x86-64 binary cannot run on Frame.

## Dependencies

Install C and C++20 compilers, CMake 3.24+, Ninja, Python 3, pkg-config, and development headers/libraries for Cairo, Pango/PangoCairo, HarfBuzz, GLib, libxkbcommon, json-c, Wayland, XCB, SDL2, and Vulkan (Vulkan only for the VR build). Haptic sounds also need the PipeWire headers (`libpipewire-0.3`) at build time and load the library at run time. A build without those headers succeeds, but sounds stay silent, so a release sysroot must include them. The libei client is pinned and built statically from `third_party/libei`; normal builds need neither system libei nor network access. The build uses the host `wayland-scanner`. Tests also need X11 development files. Chinese/Korean release builds also need PyZy development headers/library and libhangul. Frame supplies both and the PyZy system dictionary; include their libraries in a curated sysroot. Host builds may omit these engines, but then cannot activate their composition profiles. Runtime adapters are loaded on demand from the release's `lib/framekeyboard/` directory; they are built alongside development executables in `engines/`. Optional Japanese conversion tests require Anthy and its dictionary; Japanese rendering needs a font such as Noto Sans CJK JP.

Swipe typing needs the optional `framekeyboard-swipe` module, built against a pinned ExecuTorch. Builds without it still work; Settings then keeps swipe disabled. Clone ExecuTorch into a directory named `executorch`, check out the commit pinned in `tools/build-executorch.sh` with submodules, and provide a Python environment with PyTorch for its code generation. Then build one prefix per target and point the presets at them:

```sh
FRAMEKEYBOARD_EXECUTORCH_PYTHON=/path/to/venv/bin/python \
  tools/build-executorch.sh host /path/to/executorch /path/to/executorch-host
FRAMEKEYBOARD_EXECUTORCH_PYTHON=/path/to/venv/bin/python FRAMEKEYBOARD_SYSROOT=/path/to/sysroot \
  tools/build-executorch.sh frame-arm64 /path/to/executorch /path/to/executorch-arm64
export FRAMEKEYBOARD_EXECUTORCH_HOST=/path/to/executorch-host
export FRAMEKEYBOARD_EXECUTORCH_FRAME=/path/to/executorch-arm64
```

The swipe word lists are generated by `tools/build_swipe_lexicon.py`; see `swipe/lexicons/README.md`.

On-device dictation needs the `framekeyboard-whisper` engine and whisper.cpp's `whisper-quantize`, built against a pinned whisper.cpp. Builds without them still work, but Settings then offers only a speech server. On device is the default, so `scripts/package.sh` refuses to package a release without them. Clone whisper.cpp, check out the commit pinned in `tools/build-whisper.sh`, then build one prefix per target and point the presets at them:

```sh
tools/build-whisper.sh host /path/to/whisper.cpp /path/to/whisper-host
FRAMEKEYBOARD_SYSROOT=/path/to/sysroot \
  tools/build-whisper.sh frame-arm64 /path/to/whisper.cpp /path/to/whisper-arm64
export FRAMEKEYBOARD_WHISPER_HOST=/path/to/whisper-host
export FRAMEKEYBOARD_WHISPER_FRAME=/path/to/whisper-arm64
```

Japanese conversion uses Mozc's server, `mozc_server`, taken from the pinned fcitx5-mozc package: Arch Linux's x86_64 package for host and simulator builds, Arch Linux ARM's aarch64 build of it for the Frame. `tools/fetch-mozc.sh` downloads the package, checks it against its pinned SHA-256 and the notices in `third_party/mozc/`, and keeps only the server, which links nothing but glibc, libstdc++ and libgcc_s. It is prebuilt, so with `FRAMEKEYBOARD_SYSROOT` set the frame-arm64 fetch checks that the Frame has every library version it needs (`tools/check_frame_libraries.py`), and `scripts/package.sh` checks again. Builds without it convert Japanese with Anthy alone, so `scripts/package.sh` refuses to package a release without it:

```sh
tools/fetch-mozc.sh host /path/to/mozc-host
FRAMEKEYBOARD_SYSROOT=/path/to/sysroot tools/fetch-mozc.sh frame-arm64 /path/to/mozc-arm64
export FRAMEKEYBOARD_MOZC_HOST=/path/to/mozc-host/mozc_server
export FRAMEKEYBOARD_MOZC_FRAME=/path/to/mozc-arm64/mozc_server
```

Arch Linux ARM keeps no archive of old packages, so keep the downloaded package in `/path/to/mozc-arm64.download`: once Arch Linux ARM updates fcitx5-mozc, it is the only copy of the pinned version. To move the pin, check the new packages' signatures first, Arch Linux's against its keyring and Arch Linux ARM's against its build system key (`68B3537F39A313B3E574D06777193F152BDBE6A6`, certified by its master keys in [archlinuxarm-keyring](https://github.com/archlinuxarm/archlinuxarm-keyring)), then set the version and both SHA-256 values in `tools/fetch-mozc.sh` ([upkeep](upkeep.md)).

The OpenVR header is vendored, but `libopenvr_api.so` comes from an installed SteamVR runtime or a separately supplied SDK library. The build searches common Linux Steam paths. Override discovery with `-DOPENVR_LIBRARY=/absolute/path/to/libopenvr_api.so` when configuring CMake.

```sh
git clone https://github.com/TaiKeid/steam-frame-full-keyboard.git
cd steam-frame-full-keyboard
./scripts/build.sh host
ctest --test-dir build/host --output-on-failure
./build/host/framekeyboard --preview
./build/host/framekeyboard --check
```

With a custom OpenVR path, configure before running the build script:

```sh
cmake --preset host -DOPENVR_LIBRARY=/absolute/path/to/libopenvr_api.so
```

CTest reports unavailable `korean-input` and `chinese-input` suites as **Skipped**, not passed. For release validation on Frame, set `FRAMEKEYBOARD_TEST_CJK_REQUIRED=1`; unavailable engines then fail. Copy `engines/` beside transferred test executables. Run `python3 tests/engine_loading_tests.py build/host/language-tests` to check missing-module recovery in isolated copies.

The preview uses the same renderer, key state, and settings as VR but never injects OS input. `scripts/preview.sh` serves the older HTML layout study, not the application.

The [desktop simulator](simulator.md) types into a text field of its own, for trying the keyboard without a Steam Frame. The `simulator` preset (`cmake --preset simulator`, then `cmake --build --preset simulator`) builds only it, without SteamVR or Vulkan (`-DFRAMEKEYBOARD_VR=OFF`), taking swipe typing and Mozc from `FRAMEKEYBOARD_EXECUTORCH_HOST` and `FRAMEKEYBOARD_MOZC_HOST` as the host preset does. `scripts/simulator-appimage.sh` packs it as an AppImage; its variables are listed under [AppImage](simulator.md#appimage).

## Debug mode

Builds other than releases have debug mode (CMake option `FRAMEKEYBOARD_DEBUG_MODE`, on by default), always on, also on the Frame and in the simulator: Settings ends with a **Debug** card, whose switches are never saved. Releases build with the `frame-arm64-release` preset, which leaves it out and never reads `--debug`.

Two more CMake options, off by default, are for development builds only. `FRAMEKEYBOARD_FOCUS_TRACE` logs dashboard focus clicks, focus checks and typing-block decisions with their monotonic times. `FRAMEKEYBOARD_FRAME_TRACE` logs, once a second while the panel is worn, the VR loop's frames, its longest gap between frames, how many came late and how many missed a whole 60 Hz frame, and a line for each Japanese conversion with its time and the reading's length. Neither logs window titles or anything typed. Configure them in a build directory of their own, for example `cmake --preset frame-arm64 -B build/frame-arm64-trace -DFRAMEKEYBOARD_FRAME_TRACE=ON`.

## ARM64 sysroot

The repository includes `cmake/steam-frame-aarch64.cmake`. It uses host Clang/LLD and target headers, GCC C++ runtime files, and libraries copied from a matching Frame system. A sysroot is not included in Git or the release archive. Recheck compatibility after Frame updates.

Set `FRAMEKEYBOARD_SYSROOT` to an absolute path outside the source checkout. It must contain:

- `usr/include`, including the target C++ standard library headers.
- `usr/lib`, with target libraries, linker names/scripts, GCC runtime files, and C runtime objects such as `Scrt1.o`, `crti.o`, and `crtn.o`.
- Both `usr/lib/pkgconfig` and `usr/share/pkgconfig`, plus library-specific headers such as `usr/lib/glib-2.0/include`.
- `opt/steamvr/bin/linuxarm64/libopenvr_api.so`.

If SSH access and rsync are configured on your Frame, this is one way to copy those installed files. Run these commands **on the development host**, replacing the SSH address with your device's address:

```sh
export FRAME_HOST=steamos@your-frame
export FRAMEKEYBOARD_SYSROOT="$HOME/steam-frame-sysroot"
mkdir -p "$FRAMEKEYBOARD_SYSROOT/usr" "$FRAMEKEYBOARD_SYSROOT/usr/share" \
  "$FRAMEKEYBOARD_SYSROOT/opt/steamvr/bin/linuxarm64"
rsync -aL "$FRAME_HOST:/usr/include/" "$FRAMEKEYBOARD_SYSROOT/usr/include/"
rsync -aL --exclude=modules --exclude=firmware --exclude=debug \
  "$FRAME_HOST:/usr/lib/" "$FRAMEKEYBOARD_SYSROOT/usr/lib/"
rsync -aL "$FRAME_HOST:/usr/share/pkgconfig/" "$FRAMEKEYBOARD_SYSROOT/usr/share/pkgconfig/"
rsync -aL "$FRAME_HOST:/opt/steamvr/bin/linuxarm64/libopenvr_api.so" \
  "$FRAMEKEYBOARD_SYSROOT/opt/steamvr/bin/linuxarm64/"
```

Copying most of `/usr/lib` can take several gigabytes. These commands only read the device; they install no packages and change no system files. They assume the Frame already contains the required development files. A missing header, linker name, or pkg-config file must be supplied from a matching target development environment. Do not substitute host x86-64 libraries. The initial validated sysroot was a smaller curated copy of these files; the broad copy recipe above has not been independently tested from a clean device.

## Cross-build and package

```sh
export FRAMEKEYBOARD_SYSROOT=/absolute/path/to/frame-sysroot
./scripts/build.sh frame-arm64
file build/frame-arm64/framekeyboard
./scripts/package.sh
```

`scripts/package.sh` builds the release in `build/frame-arm64-release`, without [debug mode](#debug-mode). It also needs `FRAMEKEYBOARD_WHISPER_FRAME` and `FRAMEKEYBOARD_MOZC_FRAME`, and takes `FRAMEKEYBOARD_EXECUTORCH_FRAME` for swipe typing; see [releasing](releasing.md#package-and-publish).

The generated Wayland protocol is compiled as C. GCC and Clang builds use the same warning flags; check clean builds of both before claiming a warning-free release.

The package script builds ARM64, installs into `out/framekeyboard-VERSION-aarch64/`, includes licenses, profiles, the README and the changelog, and writes an archive plus `out/SHA256SUMS`. It leaves out `docs/` and `CONTRIBUTING.md`, which nothing installed reads; the packaged README and changelog link to them at the release's tag on GitHub instead. Only the packaged executable is stripped, using the cross toolchain's `CMAKE_STRIP`; the build-directory executable retains debugging information. Packaging rejects remaining debug/static-symbol sections, a non-AArch64 binary, embedded source/sysroot/builder-home paths, an executable that still has debug mode or needs PyZy, libhangul or the system libei, and a Mozc server that needs library versions the sysroot lacks. Compiler prefix maps remove build paths from diagnostics, and haptic manifests are found relative to the executable rather than through an embedded source path. Development builds copy the manifests into `build/<preset>/vr/`.

The binary retains the device OpenVR runtime path `/opt/steamvr/bin/linuxarm64`. The pinned libei client is compiled into the executable to avoid a crash in SteamOS libei 1.4.1 when negotiation is aborted. Its MIT license and provenance are included. The remaining third-party libraries come from the installed runtime.

Host and ARM64 build directories are separate. If switching sysroots or toolchains for an existing build directory, use `cmake --fresh --preset frame-arm64` before rebuilding. The build script validates the executable's AArch64 architecture.

## Tests

CTest includes `languages`, `keyboard-core`, `settings`, `placement-instance`, `japanese-input`, and `rendering`. `ei-handshake` checks peer EOF and explicit cleanup during negotiation on private socketpairs, including ARM64 builds; it never contacts a compositor or announces an input device. The rendering suite compares incremental and forced full images pixel-by-pixel across all bundled languages, controller overlaps, animation reversal, modifiers, composition, settings, and profile changes. Host builds also run installer validation/failure/retry tests. If libeis 1.6+ development files are available, `ei-recovery` tests pause/resume, disconnect, and text-socket selection using an isolated compositor and dummy Wayland listeners that cannot deliver input to the desktop. They use capture sinks and temporary configuration directories, not user applications. The placement suite uses local Unix sockets. A restricted sandbox must allow those sockets.

Anthy integration is optional in normal test runs. To require the real conversion test when the library and dictionary are installed:

```sh
FRAMEKEYBOARD_TEST_ANTHY_REQUIRED=1 ctest --test-dir build/host --output-on-failure
```

`FRAMEKEYBOARD_TEST_ANTHY_DICTIONARY` can point to a nonstandard `anthy.dic`; `LD_LIBRARY_PATH` can select a matching library. These overrides apply only to testing.

ARM64 tests must run on an ARM64 machine. For example, after cross-building:

```sh
scp build/frame-arm64/keyboard-tests build/frame-arm64/placement-instance-tests \
  build/frame-arm64/japanese-tests build/frame-arm64/fake-mozc "$FRAME_HOST:/tmp/"
ssh "$FRAME_HOST" '/tmp/keyboard-tests && /tmp/placement-instance-tests && FRAMEKEYBOARD_TEST_ANTHY_REQUIRED=1 /tmp/japanese-tests'
```

`japanese-tests` starts the stand-in Mozc server, `fake-mozc`, from its own folder, so copy the two together.

Optional probes are excluded from CTest. `uinput-smoke-test` exclusively grabs its own device before emitting events. `ei-target-probe` and `japanese-target-probe` require focus in their own disposable Xwayland receiver. `vr-panel-probe` requires a specific input-disabled instance before posting UI events. `stick-component-probe` checks model calculations; `haptics-probe` physically vibrates controllers. Read each probe's source and usage before running it. Do not run input probes against the user's active typing session.

### Host memory-safety checks

The `sanitized` preset uses a separate Debug build in `build/sanitized`. It
enables AddressSanitizer and UndefinedBehaviorSanitizer for C and C++ sources,
executables, shared libraries and modules built by this project. Start with a
fresh configuration when replacing an older manually configured sanitizer build:

```sh
cmake --fresh --preset sanitized
cmake --build --preset sanitized -j 4
ctest --preset sanitized --output-log /absolute/path/to/sanitizers-raw.log
```

This runs every available CTest group, including `rendering`, with leak detection
enabled and no LeakSanitizer suppression. The test preset clears inherited
`LSAN_OPTIONS` so an earlier shell setting cannot silently filter the raw run.
Private socket and loopback fixtures still need those operations allowed by the
execution sandbox. Keep the full log, exit status and skipped groups; a denied
fixture operation is not a production memory finding.

Font-using tests may report allocations retained by Fontconfig at process exit.
The fixed allocation total in a minimal drawing probe supports a cache
explanation for that probe, but does not establish that every application report
is a cache. Investigate application growth with unsuppressed measurements across
increasing workload counts after warm-up. Resident memory alone is insufficient:
allocator caching can keep freed pages resident.

An opt-in secondary run filters Fontconfig allocation stacks using
[`tests/lsan-fontconfig.supp`](../tests/lsan-fontconfig.supp) and Anthy's
initialization and prediction stacks using
[`tests/lsan-anthy.supp`](../tests/lsan-anthy.supp).
Configuration combines the two into `build/sanitized/lsan-third-party.supp`.
The preset keeps its existing name:

```sh
ctest --preset sanitized-fontconfig-filtered \
  --output-log /absolute/path/to/sanitizers-fontconfig-filtered.log
```

Keep this log separate from the raw run. The filter can hide application-caused
leaks allocated inside Fontconfig; a filtered pass is not a zero-leak result. No
font-library teardown is added just to silence these reports.

Anthy's `anthy_conf_override`, `anthy_init` and prediction retain allocations after
`anthy_quit`. A direct probe retained 116 bytes after both 10 and 2,000 prediction
calls; that supports fixed retained storage in that probe, not a general
claim about application leaks. Anthy is shut down after successful initialization
but stays loaded, including after failed initialization and restart attempts.
Retries reuse the loaded API and attempt initialization again. The Anthy filter
matches `libanthy`, covering both `libanthy.so` and `libanthydic.so` in exit-time
stacks, including their versioned names. It can also hide application-caused
leaks allocated inside either library.
Keep unsuppressed logs when investigating Anthy ownership or growth; a filtered
pass is not a zero-leak result. The raw `sanitized` preset remains unsuppressed.

The configure preset inherits `FRAMEKEYBOARD_EXECUTORCH_HOST`,
`FRAMEKEYBOARD_WHISPER_HOST` and `FRAMEKEYBOARD_MOZC_HOST` from the ordinary host
setup. Set them before fresh configuration to include the optional swipe and
on-device recognition adapters and Mozc's server.
The adapters are instrumented, but prebuilt inference libraries, Mozc's prebuilt
server and system libraries remain uninstrumented unless rebuilt separately with
compatible sanitizer flags. Sanitizer builds start Mozc's server with a plain
fork rather than the keyboard's memory-sharing start, which the sanitizers
cannot follow. The vendored libei C sources and generated protocol C sources
are instrumented by this preset. Record missing engines and their skipped tests
rather than treating them as covered. Python and shell logic is not instrumented,
although their tests can exercise instrumented native child programs.

These host checks do not exercise the real headset runtime, controllers or audio
devices, or measure device battery use. Keep ARM64 builds and device acceptance
separate from this host configuration.

### Measure rendering

`render-benchmark` uses the production renderer with bundled English/Graphite profiles, a temporary config directory, and a `NullSink`. It cannot type into applications. It runs for about 35 seconds after warmup, measuring idle, one and four key presses per second, and forced redraws at a target 60 Hz. Each synthetic press lasts 100 ms; the normal 80 ms press/release animations determine redraw counts. It does not change the installed app or its settings.

After configuring the ARM64 build, run on the device:

```sh
cmake --build build/frame-arm64 --target render-benchmark
scp build/frame-arm64/render-benchmark "$FRAME_HOST:/tmp/"
ssh "$FRAME_HOST" 'XDG_RUNTIME_DIR=/run/user/$(id -u) /tmp/render-benchmark --vr'
```

Keep the headset awake and record the build type and runtime conditions. `--vr` requires SteamVR to be running already and creates its own hidden, noninteractive overlay. Omitting it measures CPU painting without connecting to SteamVR. `--full-paint` disables incremental painting, and `--rgba` forces the compatibility upload path. Combine both flags to compare with the original full-render/conversion approach. The final stress workload always forces full paints. Use an optimized build for performance comparisons; the host preset is Debug.

Output separates wall-clock painting and texture submission, with means, medians, p95 values, and process CPU time. Native upload has no pixel conversion; the compatibility path reports conversion and upload together. Upload includes staging copy, GPU fence wait, and OpenVR submission; it is not a GPU-only timer. Total redraw time includes minor measurement overhead. Before timing, the probe checks the overlay alpha flag and reads back its own texture where supported. Frame returns raw BGRA for native textures; matching those bytes verifies transfer but does not replace a headset check of colors and transparent edges. CPU percentages use one logical CPU as 100%, not the entire device.

This isolates rendering: it excludes the production controller/pose/haptic/input loop and visible compositor drawing. Idle reports the benchmark's idle cost, not the complete installed app's cost. Deadline overruns mean the benchmark loop exceeded 16.667 ms, not that SteamVR dropped a displayed frame. These measurements alone cannot establish battery life or power consumption.

### Measure replacement idle overhead

`scripts/measure-replacement.py` reads Linux process counters for the current installed keyboard, its helper and its native guard. It also reads available battery status and raw sysfs power counters. It does not send input, contact CDP, change settings or restart anything. For a Frame measurement, copy only this probe from the development host:

```sh
scp scripts/measure-replacement.py "$FRAME_HOST:/tmp/framekeyboard-measure-replacement.py"
ssh "$FRAME_HOST" 'python -B /tmp/framekeyboard-measure-replacement.py --seconds 20 --include-steam --label baseline' > baseline.json
```

Repeat with the same headset/dashboard state for a candidate build. A changed process identity invalidates the comparison. CPU percentages use one logical core as 100%. Context switches and read/write syscall counts do not identify CDP polls, and aggregate Steam webhelper CPU does not isolate `inspect()`. Short samples or charging cannot establish battery savings. Summon latency, native fallback and owner transitions need separate acceptance.

## Refresh the README image

The README image is the first scene of the Japanese render tour: the default US QWERTY profile with every toolbar button showing. That takes an additional language, Replace native keyboard, Swipe typing, Haptic sounds and key flicks, and Self-hosted dictation for the mic key; On device would hide it until the model is downloaded. Only the VR mode draws the Focus mode button, so a plain `--render` can't. The tour builds with the host preset, swipe typing included (`FRAMEKEYBOARD_EXECUTORCH_HOST`), and its dictation address is a placeholder that appears nowhere in the image:

```sh
tour=$(mktemp -d)
./build/host/japanese-tour "$tour"
cp "$tour/00-readme.png" docs/images/keyboard-graphite.png
rm -r "$tour"
```

The tour renders without the interactive preview's input notice. This is a native-renderer capture, not an in-headset photograph. It contains no browser window or personal text. Inspect it before committing. Keep the README caption explicit about its source.

The `languages` suite checks all added XKB profiles; `korean-input` and `chinese-input` check the real Hangul and Pinyin engines, when compiled in, plus app commit ordering, and `table-composition` checks Cangjie and Quick composition against a fixture table. Set `FRAMEKEYBOARD_TEST_CJK_REQUIRED=1` to make missing engines a test failure. Run this on Frame for release verification. `japanese-target-probe --multilingual` checks a fixed mixed-script phrase in its own focus-checked receiver.

`unicode-target-probe` exercises the production App with German, French, Russian, Ukrainian, Brazilian, Korean and both Chinese profiles, without a target-language declaration. It creates temporary settings, re-focuses only its own disposable Xwayland window before each press, verifies focus before delivery, and checks exact output. It restores previous focus and deletes its temporary settings. Never run it against a user field.
